Fare un errore semantico significa automaticamente che tale errore possa essere o non essere rilevato immediatamente. Più a lungo un errore resta all'interno del codice, più è difficile da trovare - inoltre potrebbe causare altri errori che dipendono da quell'errore, rendendo il debugging particolarmente difficile. 

#### Evitare di fare errori
Fare debugging è il doppio più difficile rispetto a scrivere di base del codice non errato, quindi evitare di compiere errori è il primo passo per ottenere un codice privo di errori semantici.
Per evitare di fare errori è opportuno:
- Seguire le **best practice**;
- Conoscere le cose **da non fare** per un dato linguaggio;
- Non rendere le funzioni troppo lunghe;
- Commentare il codice per renderlo più leggibile e comprensibile;
- Aumentare complessivamente la complessità;
- Ottimizzare per leggibilità e manutenibilità, **non performance**.
Vediamo alcune pratiche per evitare questi errori.
#### Refactoring
Mano a mano che il nostro codice acquisice nuove capacità, le funzioni che abbiamo scritto diventano **sempre più lunghe e sempre più complesse**. 

Un modo per risolvere questo problema è prendere una funzione e **spezzarla in funzioni più semplici e più corte**. Questo processo viene chiamato ***refactoring***. L'obiettivo del *refactoring* è quello di rendere il codice **meno complesso aumentandone l'organizzazione e la modularità**.

Quando una funzione diventa troppo lunga è molto difficile da capire - idealmente ogni funzione non deve essere più lunga di 10 righe, ma questo cambia da caso a caso.
L'obiettivo è quello di massimizzare la comprensione di quello che viene scritto, oltre alla manutenibilità, **non ridurre la lunghezza del codice** - meglio un codice lungo e corretto che corto e sbagliato.

#### Introduzione alla programmazione difensiva
Gli errori non sono unicamente causati da chi scrive il codice, ma possono anche avvenire quando un utente utilizza l'applicativo in modo diverso da quello previsto. 

Per esempio, se il programma vuole come input un numero intero e viene inserita invece una lettera, come si comporterà il programma? Se questo comportamento non è stato previsto, probabilmente non molto bene.

La ***programmazione difensiva*** è una pratica dove il programmatore **prova ad anticipare ogni modo in cui il programma può essere usato**, sia dagli utenti, sia da altri sviluppatori.
Gli usi sbagliati dell'applicazione possono essere rilevati e corretti. 

#### Trovare errori velocemente
Siccome trovare gli errori è difficile in programmi di grandi dimensione, la pratica migliore è cercare di trovare gli errori fatti nel minor tempo possibile, quindi ***testarlo poco alla volta, mano a mano che viene scritto nuovo codice***.

#### Introduzione alle funzioni di test
Un modo efficiente per scrivere del codice appena scritto è scrivere **una funzione che fa uso di tale codice a fini di test**, ossia verificare, per alcuni valori di ingresso, il corretto comportamento della funzione.
```cpp
#include <iostream>

int add(int x, int y) {
	return x + y;
}

void testadd() {
	std::cout << "This function should print: 2 0 0 -2\n";
	std::cout << add(1, 1) << ' ';
	std::cout << add(-1, 1) << ' ';
	std::cout << add(1, -1) << ' ';
	std::cout << add(-1, -1) << ' ';
}

int main() {
	testadd();

	return 0;
}
```
In questo caso, la funzione `testadd()` verifica il comportamento della funzione `add()` con vari input diversi. Questa è una forma primitiva di ***unit testing***, ossia del testing di piccoli pezzi di codice al fine di verificarne il corretto funzionamento. 

#### Introduzione ai *costraints*
Un ***costraint*** è un pezzo di codice che verifica che una serie di assunzioni ***siano verificate o meno***, e nel caso lo siano (o non lo siano) permettono al programma di agire di conseguenza.

Un esempio è il calcolo della radice quadrata di un numero: se l'input è negativo allora non è possibile calcolarla, ed è necessario generare un'errore.

Vedremo in futuro metodi per generare errori se delle condizioni non sono verificate.

#### Diagnosticare problemi generici
I programmatori tendono a eseguire errori molto comuni e questi errori possono essere rilevati da **appositi programmi**, realizzati con lo scopo di rivelazione di questi errori.
Questi programmi, detti ***programmi di analisi statica*** (chiamati *linter*) sono programmi realizzati per rilevare all'interno del codice errori semantici. *Statico* significa che il codice non deve essere eseguito per effettuare questa diagnosi.

I problemi rilevati da questi programmi potrebbero non essere la causa diretta di un dato problema, ma aiutano a rinforzare aree di codice che potrebbero causare tali errori.

Uno degli strumenti di analisi statica che già possediamo è il ***compilatore***, che eseguono anche una breve analisi statica prima di effettivamente compilare il codice (restituendo oltre agli errori di sintassi **avvisi di eventuali problematiche semantiche**).

L'uso di uno strumento di analisi statica è opzionale, ma consigliato per rinforzare il codice.
