Vediamo alcune "tattiche" che rendono la fase di individuazione degli errori più efficiente.

#### Commentare del codice
È possibile escludere la compilazione di pezzi di codice semplicemente commentandoli tramite `//` o `/* */`, al fine di controllare se essi contribuiscono o meno alla manifestazione del problema. 

```cpp
#include <iostream>

int main() {
	getNames();
	doSomething();
	sortNames();
	printNames();
	return 0;
}
```
In questo esempio, vogliamo che i nomi inseriti in input tramite `getnames()` vengano restituiti ordinati in ordine alfabetico. Durante l'esecuzione però i nomi vengono restituito in ordine opposto - come mai? Potrebbe essere una delle funzioni che abbiamo usato. Pensandoci un po', il probabile colpevole potrebbe essere `doSomething()`. Commentiamo la riga che richiama la funzione e vediamo cosa succede.
```cpp
#include <iostream>

int main() {
	getNames();
	// doSomething(); // Non verrà considerato. Problema risolto?
	sortNames();
	printNames();
	return 0;
}
```
Commentare `doSomething()` ha tre possibili risultati:
- Il problema sparisce $\to$ è colpa di `doSomething()` se si manifesta il problema.
- Il problema non sparisce e si ripresenta esattamente come prima del commento $\to$ `doSomething()` non c'entra nulla col problema.
- Il problema si ripresenta sotto un'altra forma $\to$ `doSomething()` contribuisce *parzialmente* al problema, ma non è la causa scatenante. 

#### Validare il flusso del codice
Supponiamo di avere un'incertezza sul numero di volte in cui una certa funzione, necessaria per ottenere il risultato sperato, viene richiamata. Magari se viene richiamata tante o poche volte (o proprio non viene richiamata) il risultato ottenuto è diverso da quello sperato. 

In questo caso è opportuno aggiungere, all'inizio della definizione di ogni funzione che si pensa faccia causare il problema, un'istruzione che stampa a schermo il nome della funzione, così quando essa viene richiamata il nome viene stampato per confermare la corretta chiamata. 

> [!note] Uso di `std::cerr`
> Quando si effettuano stampe di debug è opportuno utilizzare `std::cerr` anzichè `std::cout`. Questo perchè `std::cout` è buffered, e se sta venendo utilizzato dal programma per altre operazioni, il buffer potrebbe risultare ancora pieno; al contrario `std::cerr` è ***unbuffered*** e stamperà qualsiasi cosa direttamente a schermo.

Quando si inseriscono queste tipologie di stampe è opportuno non indentarle, in modo che siano facilmente rimovibili in seguito.
```cpp
#include <iostream>
int getValue()
{
	return 4;
}

int main()
{
    std::cout << getValue << '\n';
    return 0;
}
```
Questo codice dovrebbe stampare il valore `4`, tuttavia stampa il valore `1` o un *indirizzo di memoria*. Dove abbiamo sbagliato? Inseriamo delle istruzioni di stampa su entrambe le funzioni.
```cpp
#include <iostream>

int getValue()
{
std::cerr << "getValue() chiamata\n";
	return 4;
}

int main()
{
std::cerr << "main() chiamata\n";
    std::cout << getValue << '\n';

    return 0;
}
```
In questo modo l'output sarà:
```
main() chiamata
1
``` 
Evidenziando chiaramente che `getValue()` non è stata richiamata! Questo perchè abbiamo scritto `getValue` senza parentesi tonde nel `std::cout`di `main()`. Inserendo le parentesi otteniamo ora il seguente output:
```
main() chiamata
getValue() chiamata
4
```
Il valore è ora quello previsto - errore risolto e quindi possiamo rimuovere le stampe di debug.

#### Stampa dei valori
Supponiamo che in corso d'esecuzione viene prodotto un valore differente da quello previsto, oppure viene passato a una funzione un parametro errato. È opportuno verificare, in corso d'opera, il valore delle variabili in uso: ciò è possibile tramite stampe, in cui viene stampato il valore di una variabile in un dato momento.

In modo simile ai controlli di codice, questi possono essere effettuati per mezzo di `std::cerr`, per i motivi spiegati precedentemente.

#### Perchè stampare valori non è good practice
Seppur molto utili, permettere la stampa di valori ai fini di debug **non è una buona pratica** per una serie di motivi:
- Ingombrano il codice e l'output del codice;
- Le stampe vanno inserite e poi rimosse - ogni modifica aggiuntiva a un codice permette l'introduzione di errori: inoltre **non sono riutilizzabili**.
