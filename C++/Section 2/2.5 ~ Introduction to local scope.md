### Local variables
Le variabili definite all'interno delle funzioni sono chiamate ***local variables*** (*variabili locali*), in opposizione alle ***global variables*** che vedremo in seguito.
I *[[2.4 ~ Introduction to function parameters and arguments#Functions parameters and arguments|function parameters]]* sono generalmente anch'essi *local variables*.
```cpp
int add(int x, int y) { // Parametri (local variables)
	int z{x + y}; // z è una local variable
	
	return z;
}
```

[[1.3 ~ Introduction to objects and variables#Variables|Nelle scorse lezioni]] abbiamo visto come la definizione di variabili del tipo `int x;` causa l'instanziazione della variabile quando questa tipologia di *statement* viene eseguita. Abbiamo visto anche che i *function parameters* vengono creati e inizializzati nel momento in cui la funzione viene chiamata e le variabili presenti all'interno di una funzione vengono instanziati nel momento in cui vengono definiti.
```cpp
int add(int x, int y) { // x e y creati qui
	int z{x + y}; // z creata qua
	
	return z;
}
```
È naturale chiedersi, una volta che le variabili sono state create, quando **esse cessano di esistere e vengano distrutte**.
Le variabili locali vengono ***distrutte in ordine opposto alla loro creazione alla chiusura della coppia di parentesi graffe `{}` in cui sono state definite***. Il "tempo trascorso" tra la creazione e la distruzione di un oggetto prende il nome di ***lifetime*** di tale variabile. 
```cpp
int add(int x, int y) { // Definizione di x e y
	int z{ x + y }; // Definizione di z
	
	return z;
} // z, y, x vengono distrutte qui in quest'ordine.
```
Il *lifetime* di una variabile è una proprietà di ***runtime*** - le variabili vengono create e distrutte in esecuzione, non in compilazione.

Quando un qualsiasi oggetto viene distrutto, nella maggior parte dei casi **non succede niente** - semplicemente ***l'oggetto distrutto diventa invalido***.
Utilizzare un oggetto distrutto da vita ad *[[1.6 ~ Uninitialized variables and undefined behavior|undefined behavior]]*. Dopo la distruzione, la memoria che è stata utilizzata per l'oggetto tornerà disponibile per l'utilizzo di altri oggetti; questa operazione si chiama ***deallocation***.

### Scope & Local scope
Si chiama ***scope*** di un identificatore la zona di codice in cui quell'identificatore può essere *visto e usato*. Quando un identificatore può essere visto e usato, si dice che è ***in scope***, quando invece non viene visto e pertanto non può essere usato si dice che è ***out of scope***.

Lo *scope* è una proprietà ***compile-time***: provare a compilare codice contenente variabili *out of scope* provocherà un errore di compilazione.

L'identificatore di una variabile *locale* ha uno ***local scope***. Un identificatore con *local scope* è usabile **dal punto della sua definizione fino al termine delle parentesi graffe che `{}` contengono tale identificatore** (o nel caso di *function parameters*, finché la funzione non termina). Questo significa che una variabile locale **non è *in scope* prima che venga definita e dopo che è distrutta**. Le variabili dichiarate localmente in una funzione **non sono *in scope* per altre funzioni al di fuori di essa**.
```cpp
#include <iostream>
// x non è in scope in questa funzione
void stampaACaso() {
	std::cout << "Ciao!" << '\n';
}

int main() {
	// x qui ancora non è in scope, non è stata creata
	
	int x{ 0 }; // x qui entra in scope
	
	stampaACaso();
	
	return 0;
} // x esce qui dallo scope e non può più essere usata
```

#### "Out of scope" vs "Going out of scope"
Le due terminologie "*out of scope*" e "*going out of scope*" hanno due significati diversi, nonostante le due sono molto simili tra loro:
- Un identificatore è ***out of scope*** quando, all'interno del codice, non è raggiungibile o accessibile, dunque non è usabile. 
- Un identificatore ***va out of scope*** quando la sua *lifetime* **termina**, ossia quando raggiunge la fine del suo *scope*.

### Functional separation
Supponiamo ora il seguente programma:
```cpp
#include <iostream>

int add(int x, int y) {
	return x + y;
}

int main() {
	int x{ 4 };
	int y{ 5 };
	
	std::cout << add(x, y) << '\n';
	
	return 0; 
}
```
In questo esempio, vediamo come sia nella funzione `add` che nella funzione `main` esistono le variabili identificate con `x` e `y`. Questo programma compila e funziona senza problemi per i seguenti due motivi:
- Le variabili `x` e `y` di `main` e `add` sono diverse tra loro - hanno solamente il nome uguale;
- Le variabili hanno *scope* diverso sulla base delle funzioni in cui si trovano. Dentro `main`, `x` e `y` si riferiscono alle variabili `x` e `y` nello *scope* locale di `main`; dentro `add`, `x` e `y` si riferiscono alle variabili `x` e `y` nello *scope* locale di `add`.
In poche parole nè `add` nè `main` conoscono il nome delle variabili dell'altra funzione e siccome gli *scope* non si sovrappongono è ***sempre chiaro a cosa si riferiscono `x` e `y`***.

> [!tip] È best practice definire le variabili locali ***quanto più vicino possibile al loro primo utilizzo all'interno della variabile***.
> ```cpp
> #include <iostream>
> 
> int main() {
> 	std::cout << "Inserisci un numero: ";
> 	int x{}; // Definizione subito prima di essere usata
> 	std::cin >> x;
> 	
> 	int square{x * x}; // Anche qui
> 	std::cout << square << '\n';
> 	return 0;
> }
> ```
> 

### Local variables vs function parameters
C'è una principale differenza tra l'uso di variabili locali e *function parameters*: vediamolo tramite questo esempio:
```cpp
int getValFromUser(int val) { // function parameter
	std::cout << "Inserisci un valore: ";
	std::cin >> val;
	return val;
}

int main() {
	int x {};
	int num { getValueFromUser(x) }; // x è un argument
	
	std::cout << "Hai inserito " << num << '\n';
	
	return 0;
}
```
In questo esempio siamo costretti a passare a `getValFromUser` un argomento, tramite il quale verrà inizializzato il parametro `val` - tuttavia all'interno della funzione il parametro verrà sovrascritto da una variabile da parte dell'utente, rendendo la parte legata al passaggio del dato tramite argomento totalmente inutile. Al posto di utilizzare un *function parameter* è opportuno utilizzare una variabile locale all'interno di `getValFromUser`, così che non sia necessario passare un argomento.
```cpp
int getValFromUser() {
	int val {}; // variabile locale
	std::cout << "Inserisci un valore: ";
	std::cin >> val;
	return val;
}

int main() {
	int num { getValueFromUser() }; // nessun argument da passare!
	
	std::cout << "Hai inserito " << num << '\n';
	
	return 0;
}
```
Generalmente si utilizzano i *function parameters* quando i valori passati tramite argomento vengono utilizzati all'interno della funzione, ed è pertanto necessario inizializzarli ai valori specificati dagli argomenti; altrimenti si utilizza una variabile locale.

### Temporary objects
Supponiamo di avere il seguente codice:
```cpp
int getValFromUser() {
	std::cout << "Inserisci un valore: ";
	int val {};
	std::cin >> val;
	return val;
}

int main() {
	std::cout << getValFromUser() << '\n';
	return 0;
}
```
In questo caso, `getValFromUser()` restituisce il valore che è contenuto all'interno della variabile locale `val` al chiamante - siccome `val` viene distrutta al termine dell'esecuzione della funzione, verrà passato al chiamante una **copia di tale valore** (come visto nel *[[2.2 ~ Function return values (value-returning functions)|return by value]]*). Il valore che viene copiato, tuttavia, ***non si sa dove viene copiato***: in `main` non abbiamo definito nessuna variabile. Tale valore viene copiato in uno **speciale tipo di oggetto**, detto ***temporary object***, che viene poi passato a `std::cout` per essere stampato.
In particolar modo, il ***return by value* restituisce un oggetto temporaneo contenente una copia del valore restituito dalla funzione**.

Gli oggetti temporanei vengono distrutti **subito dopo lo statement in cui sono stati creati**. Nel nostro esempio verrà distrutto dopo `std::cout << getValFromUser() << '\n'`.
Nel caso un oggetto temporaneo dovesse inizializzare una variabile, tale oggetto viene distrutto subito dopo l'inizializzazione della variabile.

La creazione di un oggetto temporaneo può essere costosa - i compilatori moderni riescono a "risparmiare" sulla creazione di oggetti temporanei in alcuni casi.
