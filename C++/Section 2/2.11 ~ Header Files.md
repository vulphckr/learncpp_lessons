[[2.8 ~ Programs with multiple files|Abbiamo visto]] come un programma può essere realizzato per mezzo di più file. 
Abbiamo anche parlato di [[2.7 ~ Forward declarations and definitions|forward declaration]] al fine di permettere l'accesso, da parte di un file, al codice di un altro file. 

Quando un programma si basa su pochi file, è semplice inserire all'interno di ciascun file le *forward declarations* necessarie al loro funzionamento. Tuttavia, se incrementiamo il numero di file all'interno di un progetto, all'interno di ciascuno di essi dovremmo ricopiare, se necessario, la stessa *forward declaration* all'interno di ciascuno: questo semplicemente non è scalabile.

## Header files
I file C++ (con estensione `.cpp`) non sono l'unica tipologia di file presente all'interno di un progetto. L'altro tipo di file più comune sono gli ***header files***, che solitamente si trovano con l'estensione `.h`, ma anche con l'estensione `.hpp` o senza estensione. 

L'utilizzo principale degli header files è quello di **raggruppare *forward declaration* di funzioni legate tra loro e propagarle successivamente quando richiesto**.

#### Esempio tipico - `iostream`
Consideriamo "Hello world!":
```cpp
#include <iostream>

int main() {
	std::cout << "Hello world!" << '\n';
	return 0;
}
```
Non abbiamo definito da nessuna parte `std::cout` - come fa il compilatore a sapere che cos'è `std::cout`?

La risposta è che `std::cout` è stato ***forward-dichiarato*** nell'header file `iostream`. Quando usiamo `#include <iostream>` richiediamo che il preprocessore sostituisca tale direttiva con i contenuti di `iostream`, incluse **tutte le *forward declaration* che contiene**.

### Usare gli header file per propagare forward declarations
Torniamo all'esempio fatto al termine di [[2.8 ~ Programs with multiple files|questa lezione]]. Avevamo due file distinti,
`main.cpp`:
```cpp
#include <iostream>

int add(int a, int b); // Forward declaration

int main() {
	std::cout << "La somma tra 2 e 3 fa: " << add(2,3) << '.\n';
	return 0;
}
```
`add.cpp`:
```cpp
int add(int a, int b) {
	return a + b;
}
```

In questo esempio, all'interno di `main.cpp` viene usata una *forward-declaration* per indicare al compilatore l'esistenza dell'identificatore `add`. Abbiamo detto che aggiungere *forward-declaration* ad ogni file che deve usare una specifica funzione indicata in altri file non è scalabile, quindi dobbiamo ovviare a questo problema. **Scriviamo pertanto un header file che risolva questo problema**.

Un header file consiste di due parti distinte:
- Un ***[[2.11 ~ Header Files|header guard]]***, di cui parleremo nella prossima lezione;
- Il contenuto effettivo dell'header, ossia **le *forward-declaration* di tutti gli identificatori che vogliamo che gli altri file vedano**.
Aggiungere un file di header a un progetto funziona in modo identico ad aggiungere un nuovo file a un progetto. Al contrario dei sorgenti (`.cpp`), gli header **non vanno inseriti in compilazione**, siccome sono già implicitamente implementati per mezzo delle direttive `#include`. La convenzione è che gli header files debbano avere estensione `.h`, anche se possono anche non avere estensione o avere un'estensione diversa.

Ogni file header è spesso accoppiato a un file sorgente - in particolare l'header fornirà la *forward-declaration* per ciò che viene definito all'interno del sorgente. È buona pratica che il file sorgente e il file header che vengono accoppiati abbiano stesso nome.

Nel nostro caso, associamo l'header `add.h` al file `add.cpp`. Avremmo quindi 3 file:
`add.h`:
```cpp
// Qui ci sarà l'header guard, che vedremo in seguito

// Da qui parte il corpo dell'header
int add(int x, int y); // prototipo per la funzione add()
```
`add.cpp`:
```cpp
#include "add.h"

int add(int x, int y) {
	return x + y;
}
```
`main.cpp`:
```cpp
#include "add.h"
#include <iostream>

int main() {
	std::cout << "La somma di 2 e 3 fa " << add(2,3) << '.\n';
	return 0;
}
```
È **best practice includere il corrispettivo header all'interno del sorgente**. Questo più che altro va fatto non perché necessario, ma perché, in presenza di errori, rende molto più semplice il debugging, andando ad evidenziare errori nel sorgente relativo all'header in cui è presente l'errore. Se non inserito l'errore verrà dato dal linker anzichè dal compilatore e risulterà più ostico da risolvere.

Quando in `main.cpp` verrà incontrata la direttiva `#include "add.h"`, il contenuto di `add.h` verrà sostituito al posto di tale direttiva. Siccome `add.h` contiene una *forward-declaration* per `add()` ne risulta un programma completamente equivalente a quello ottenuto inserendo manualmente la *forward-declaration*!

Inserire le definizioni direttamente all'interno dell'header potrebbe sembrare una buona idea, ma ha due fondamentali problemi:
- Non si risolverebbe nulla - saremmo ancora al punto di partenza in cui, al posto di una *forward-declaration* avremmo biosgno di una direttiva `#include` per funzione usata;
- Si violerebbe la seconda regola dell'[[2.7 ~ Forward declarations and definitions#One Definition Rule (ODR)|ODR]] - questo perché il contenuto dell'header verrebbe sostituito sia in `main.cpp` che nel file sorgente associato all'header - questo viola il principio di non avere due definizioni dello stesso identificatore e restituirà errore di linker. 
Per ora, limitiamoci a dire che **negli header file non vanno inserite definizioni**, ma solo dichiarazioni per mezzo di prototipi che rendono possibili *forward-declarations*.

Infine, **non bisogna mai includere nei sorgenti i file `.cpp`**, nonostante il preprocessore non darà problemi nell'includerli. - questi sono da considerare come file sorgenti e pertanto vanno compilati. Questa regola viene posta per più motivi:
- È molto facile generare collisioni e violare una o più ODR;
- Non è convenzionale;
- Cambiare un sorgente incluso da qualche parte comporta la ricompilazione di ***entrambi i sorgenti coinvolti*** - che può richiedere molto tempo.

#### `<>` vs. `""`
Usiamo le parentesi angolari `<>` durante l'inclusione di un header quando **vogliamo includere un header che non abbiamo scritto noi**. Il preprocessore cercherà questi header in delle *directory* specifiche, chiamate ***include directories*** e specificate dall'IDE o dal progetto.

Usiamo i doppi apici `""` durante l'inclusione di un header quando **vogliamo includere un header che abbiamo scritto noi**. Il preprocessore cercherà questi header **prima nella directory corrente**, poi, se non li trova, nelle ***include directories***.

##### Perche `iostream` non termina in `.h`?
Come abbiamo visto `iostream` non termina in `.h`, ma per quale motivo?
Un tempo, C++ utilizzava header di libreria standard che finivano in `.h` - questi avevano dichiarato **tutte le variabili e le funzioni all'interno del *global namespace***. Tutto questo andava bene finché il linguaggio nonè stato uniformato e si è optato ad inserire tutte le funzioni standard del linguaggio all'interno del *namespace* `std` - questo avrebbe comportato un problema enorme, poiché avrebbe significato cambiare `iostream.h` e, di conseguenza, tutti i programmi che avevano utilizzato tale header non sarebbero più stati funzionanti. 

Si è optato quindi alla creazione di un nuovo header, senza il `.h` finale, chiamato `iostream`, in cui tutte le funzioni e le variabili erano contenute all'interno del *namespace* `std`. Pertanto, `iostream.h` ed `iostream` sono ***due cose diverse***. Oggi è **best-practice** utilizzare le librerie standard prive dell'estensione `.h`.

##### Includere header da altre directory
È possibile includere header da altre directory in due modi:
- Si può specificare il percorso relativo di tale file subito dopo l'`#include`, ma è fortemente sconsigliato.
- Si può inserire nell'IDE o nel compilatore una directory specifica che contiene gli header da includere.

##### Gli header possono includere altri header
È normale per i file header usare qualcosa che è contenuto all'interno di un altro file header. In questo caso, è necessario includere tale header all'interno di un altro header, ancora una volta con una direttiva `#include`.

#### Include transitivi
Quando si include uno specifico header all'interno di un sorgente, si includono automaticamente anche tutti gli header inclusi da tale header, e di questi gli header inclusi...
Questi file header aggiuntivi vengono detti ***transitive includes***, siccome sono inclusi in modo *implicito* e non *esplicito*.

Quando avviene un'inclusione transitiva, il contenuto dell'header incluso in questo modo è disponibile all'uso del codice sorgente. Di base, **non si dovrebbe fare ricorso all'uso di funzionalità introdotte per mezzo di include transitivi**, a meno di documentazione. Questo perché l'implementazione degli header può cambiare progressivamente, rendendo il codice funzionante su alcune macchine, ma non su tutte. A questo fine vige una **regola d'oro**: è necessario ***includere tutti gli header necessari alla compilazione in ogni file***, senza dover quindi usare include transitivi. Individuare quando vengono usati include transitivi è una pratica difficile - utilizzare questa regola rimuove il problema.

### Ordine di inclusione degli header
Se gli header sono scritti a dovere, l'ordine di inclusione degli header è ***indifferente***.
Tuttavia, se abbiamo un header A che ha bisogno delle dichiarazioni presenti in un header B, se includiamo prima A e poi B il compilatore restituirà un errore - questo poiché, compilando dall'alto al basso, il codice di A verrà compilato prima del codice di B, e siccome in A mancano le dipendenze di B questo genererà un errore - questo è preferibile, in quanto questo errore è limitato solo a questa cosa e quindi facilmente risolvibile.

Per ogni file esiste anche una best practice per le inclusioni degli header, che deve essere svolto in questo ordine (saltando i non rilevanti e i non necessari):
1) Includere l'header **associato al file sorgente** (es. `add.cpp` deve includere `add.h`)
2) Includere altri header dello stesso progetto (es. `lemieutility.h`)
3) Includere librerie esterne (es. `<boost/tuple/tuple.hpp>)`
4) Includere libreria standard (`iostream`)
Usare questo ordine garantisce che, anche se abbiamo dimenticato un include, l'errore che verrà generato sarà facile da risolvere.

### Best/Good practices per gli header
- Includere sempre le ***[[2.12 ~ Header Guards|header guards]]*** (viste nella prossima lezione);
- Non definire variabili negli header (per ora);
- Associare ad ogni sorgente il corrispettivo header, nel caso di inclusioni esterne;
- Ogni header **deve avere uno specifico scopo e deve essere il più indipendente possibile dagli altri**, ossia inserire funzionalità comuni in un unico header e altre funzionalità comuni in un altro header - in questo modo, se abbiamo necessità delle une o delle altre basterà semplicemente importare un header o l'altro;
- Utilizzare strettamente gli header necessari alla compilazione, al fine di evitare include transitivi - questo vale sia per i sorgenti che per gli header stessi;
- Inserire documentazione nell'header piuttosto che al sorgente associato - è molto più evidente se inserito lì;
- Non includere file `.cpp` (sorgenti).
