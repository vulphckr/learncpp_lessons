Supponiamo di dover recarci a casa di un nostro amico: il nostro amico ci da l'indirizzo di casa sua e noi partiamo per il viaggio. Arrivati alla sua città scopriamo però che esistono due vie che posseggono lo stesso identico nome; in quale delle due strade vive il nostro amico? Come facciamo a decidere quale sia corretta e quale no? In generale, per quanto riguarda gli indirizzi, abbiamo bisogno che ***ogni indirizzo sia univocamente riconoscibile***.

In modo simile, C++ ha la necessità che ***ogni identificatore deve essere non-ambiguo*** - se vengono introdotti due identificatori tali che il compilatore o il linker non hanno modo di distinguere l'uno dall'altro, allora **verrà prodotto un errore** da uno dei due. Questo errore è chiamato ***naming collision*** o ***naming conflict***. In particolare, l'errore verrà generato dal compilatore se il conflitto avviene nello stesso file e dal linker se avviene in file diversi.

#### Esempio di *naming collision*
Supponiamo di avere i seguenti file:
`a.cpp`:
```cpp
#include <iostream>

void myFunction(int x) {
	std::cout << x << '\n';
}
```
`main.cpp`:
```cpp
#include <iostream>

void myFunction(int x) {
	std::cout << 2 * x << '\n';
}

int main() {
	return 0;
}
```

In questo caso, durante la compilazione tutto fila liscio: [[2.8 ~ Programs with multiple files|come abbiamo visto]] entrambi i file vengono infatti compilati in modo indipendente l'uno dall'altro. Il problema avviene però in fase di linking: il linker infatti non capisce quale delle definizioni presenti nei due file associare all'identificatore `myFunction` - il linker genererà pertanto un errore di *naming collision*. Si nota che **la funzione non viene mai chiamata**, quindi questo errore è anche molto silenzioso. Come abbiamo detto, gli errori di *naming collision* avvengono in due casi:
- Se vengono introdotte due definizioni della stessa funzione (o della stessa variabile globale) *in due file diversi* si avrà un errore in fase di linking;
- Se vengono introdotte due definizioni della stessa funzione (o della stessa variabile locale) *nello stesso file* si avrà un errore di compilazione.

Abbiamo visto che col crescere dell'entità del programma anche gli errori possibili crescono - per evitare ciò C++ ha introdotto diversi meccanismi, come per esempio il *[[2.5 ~ Introduction to local scope|local scope]]* - tuttavia questo meccanismo non è disponibile per le funzioni. Esiste un meccanismo simile che evita i conflitti tra identificatori di funzione?

#### Scope regions
Tornando all'esempio delle città - il problema principale è che avevamo *due strade aventi lo stesso nome **nella stessa città***. Tale problema però non si pone se abbiamo *due strade aventi lo stesso nome **in città diverse***: in quel caso non si avrebbe confusione su dove andare. 

In C++, le *città diverse* sono analoghe alle ***scope regions***: aree di codice sorgente in cui gli identificatori vengono considerati ***distinti*** se ***definiti in diverse scope regions***. In pratica se abbiamo due *scope regions* e al loro interno è presente lo stesso identificatore allora non ci saranno problemi a distinguere l'uno dall'altro, in quanto è facile distinguere una *scope region* dall'altra. Questo vale tra **diverse** *scope regions*, mentre nella stessa *scope region* non devono essere presenti duplicati. 

Un esempio di *scope region* sono ***i corpi delle funzioni*** - è infatti possibile avere due funzioni che possiedono al loro interno lo stesso identificatore, e questo non genererà un problema - ma se si riusa lo stesso identificatore all'interno di una funzione questo causa un *naming conflict*.

### Namespaces
Un ***namespace*** è una specifica tipologia di *scope region* (chiamata ***namespace scope***) la quale permette di **dichiarare o definire identificatori** al fine di renderli ***non-ambigui***. Essendo una *scope region* tutti i nomi dichiarati all'interno di un ***namespace*** sono isolati dai nomi dichiarati all'esterno di tale *namespace*, evitando pertanto *name conflicts*: un esempio è la dichiarazione di due funzioni aventi lo stesso identificatore ma diversa definizione - se questa avviene in due diversi *namespace* allora non avverranno conflitti.

Un *namespace* contiene solo ***dichiarazioni e definizioni***: non conterrà *statement* eseguibili a meno che questi non facciano parte di una definizione (per esempio fanno parte di una funzione dichiarata all'interno del *namespace*).

Solitamente i *namespace* vengono utilizzati per **raggruppare per tipologie** identificatori che svolgono funzioni collegate, al fine di evitare collisioni con funzioni con nomi uguali ma che svolgono funzioni diverse. Un tipico esempio è raggruppare all'interno di un *namespace* chiamato `math` tutte le funzioni o le costanti legate alla matematica - in questo modo saranno chiaramente differenziate da funzioni esterne aventi lo stesso identificatore. 

#### Il Global Namespace
In C++ se qualcosa non viene definito all'interno di classi, funzioni o *namespace* entra **automaticamente** a far parte di un particolare *namespace*, chiamato ***global namespace*** o ***global scope***.

Nell'esempio fatto all'inizio della lezione, sia `main()` che entrambe le definizioni di `myFunction()` sono definite nel ***global namespace***; il conflitto deriva dal fatto che esistono due definizioni di `myFunction()` nello stesso *namespace*, violando la regola di unicità.

Per ora ci preoccuperemo di dire due cose riguardanti il ***global namespace***:
- Ciò che viene dichiarato all'interno del ***global scope*** rimane ***[[2.5 ~ Introduction to local scope#Scope & Local scope|in scope]]*** fino alla fine del file.
- Anche se è possibile dichiarare variabili nel ***global namespace*** questo va ***evitato***.

### Il namespace `std`
Il *namespace* `std` corrisponde al *namespace* contenente ***le funzionalità standard di C++***, provenienti dalla **libreria standard di C++**. Questa è stata creata per evitare problemi di ambiguità con funzioni create dagli utenti, ma anche per garantire che queste funzioni non vengano modificate con aggiornamenti futuri del linguaggio.

Quando usiamo `std::cout`, in realtà stiamo usando l'identificatore `cout` del *namespace* `std`. Siccome `cout` è definito nel *namespace* `std`, anche se usiamo l'identificatore `cout` in un altro *scope* esterno a quello del *namespace* `std` (come per esempio quello globale) non creerà conflitti. 

In particolare, quando usiamo un identificatore che fa parte di uno specifico *namespace* che non sia quello globale allora **dobbiamo specificare a quale *namespace* ci stiamo riferendo**. Esistono diversi modi per eseguire questa specifica.

#### Qualificatore esplicito di *namespace*
Se vogliamo utilizzare `cout`, facente parte del *namespace* `std`, è possibile esplicitare direttamente l'uso di questo specifico identificatore in questo specifico *namespace* per mezzo del prefisso `std::`.
```cpp
#include <iostream>

int main() {
	std::cout << "Hello world!" << '\n'; // Usiamo cout del namespace std.
	return 0;
}
```
Il simbolo `::` è ***un operatore***, chiamato ***scope resolution operator***. A sinistra dell'operatore è presente il *namespace* nel quale l'identificatore posto alla destra dell'operatore è contenuto. Se non viene usato l'operatore `::` si presupporrà automaticamente l'uso del ***global namespace***.

Quando scriviamo `std::cout` stiamo di fatto dicendo al compilatore "usa l'identificatore `cout` facente parte del *namespace* `std`". Questo è ***il modo più sicuro*** per usare uno specifico identificatore, in quanto diventa impossibile avere ambiguità. 
Se un identificatore possiede un *namespace prefix* tale identificatore viene detto ***qualified name***.

#### Using directive (perché evitarle)
Un altro modo per accedere agli identificatori di uno specifico *namespace* è tramite l'uso di una ***using directive***.
```cpp
#include <iostream>

using namespace std; // using directive - da ora in poi possiamo accedere agli identificatori del namespace std senza specificare un namespace prefix

int main() {
	cout << "Hello world!" << '\n'; // Non abbiamo usato prefissi.
	return 0;
}
```

Usare una *using directive* è ***fortemente scoraggiato***, perché rimuove il senso dell'uso dei *namespace* come metodo per ***differenziare gli identificatori***. Infatti, nel caso di questo codice:
```cpp
#include <iostream> // importo std::cout

using namespace std; // std::cout può essere usato come cout

int cout() { // funzione utente "cout" dichiarata nel global scope
	return 5;
}

int main() {
	cout << "Ciao!" << '\n'; // errore di compilazione - quale delle due cout uso?
	return 0;
}
```
Questo programma non compila - all'uso della funzione `cout` il compilatore non sa se usare quella  contenuta dentro `std` o quella dichiarata dall'utente. Questo è proprio il motivo per cui i *namespace* sono stati inventati in primis, ossia per evitare conflitti tra identificatori facenti parte di scope diversi - qui, anche se siamo in scope diversi, c'è comunque ambiguità. 
***È pertanto fortemente scoraggiato l'uso di using directives*** nel caso di *namespace*.

### Curly brackets and indented code
Le parentesi graffe, oltre a scopi secondari (come le *list-initialization*) vengono principalmente utilizzate per ***delineare scope annidati all'interno di altri scope***. Per esempio, si utilizzano le parentesi graffe per delimitare lo *scope della funzione* dallo *scope globale*.

In alcuni casi, ciò che viene dichiarato fuori dalle parentesi graffe può comunque far parte dello *scope* interno a queste ultime. Un chiaro esempio sono i **[[2.4 ~ Introduction to function parameters and arguments|parametri di funzione]]**.
```cpp
#include <iostream>

void foo(int x) { // foo dichiarata nello scope globale, x nello scope di foo.
	std::cout << x << '\n';
} // x (di foo) out of scope alla fine di foo.

int main() { // main dichiarata nello scope globale.
	foo(5);
	
	int x { 6 }; // x dichiarata nello scope di main.
	std::cout << x << '\n';
} // x (di main) out of scope alla fine di main.
// main, foo e std::cout out of scope alla fine del file
```
Il codice presente all'interno di uno *scope* annidato viene indentato, sia per aumentarne la leggibilità, ma anche per segnalare che fa parte di uno *scope* a parte.
`#include`, `main()` e `foo()` non vengono indentate in quanto fanno parte dello *scope* globale - mentre gli *statement* al loro interno vengono indentati in quanto fanno parte dello *scope* annidato delle corrispettive funzioni.
