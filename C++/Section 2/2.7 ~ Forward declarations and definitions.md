### Sequenzialità di lettura degli identificatori
Consideriamo il seguente codice:
```cpp
#include <iostream>

int main() {
	std::cout << "La somma tra 2 e 3 fa: " << add(2,3) << '.\n';
	return 0;
}

int add(int a, int b) {
	return a + b;
}
```
Questo codice, seppur sintatticamente corretto, genera un ***errore di compilazione***: in particolare il compilatore segnalerà il ***mancato ritrovamento dell'identificatore `add`***, nonostante sia presente nel codice. 

Questo perché il compilatore legge gli identificatori di funzione in modo ***sequenziale***, dall'alto verso il basso: a riga 4 viene utilizzato l'identificatore `add` quando ancora non è stato inizializzato, giustificando così l'errore. 

Per risolvere questo problema esistono due strade:
#### Opzione 1 - Riordinamento del codice
Se riordiniamo il codice in modo che la funzione `add` venga inizializzata prima del suo uso, il compilatore riuscirà a trovarla poiché in sequenza.
```cpp
#include <iostream>

int add(int a, int b) {
	return a + b;
}

int main() {
	std::cout << "La somma tra 2 e 3 fa: " << add(2,3) << '.\n';
	return 0;
}

// Output: La somma tra 2 e 3 fa: 5.
```
In questo modo il codice compilerà e funzionerà senza problemi.

Questo metodo, seppur facile ed intuitivo, diventa un problema quando il codice diventa più complicato: se infatti all'interno di altre funzioni diverse da `main` abbiamo chiamate ad altre funzioni non ancora inizializzate, tali funzioni vanno riordinate secondo il criterio di lettura del compilatore, rendendo spesso l'operazione complicata. 

#### Opzione 2 - ***Forward declaration***
Possiamo risolvere il problema utilizzando una ***forward declaration***: questa ci permette di comunicare al compilatore l'esistenza di un identificatore ***prima che esso sia effettivamente definito*** nel codice. Nel caso di funzioni questo si traduce nel comunicare l'esistenza di tale funzione ***prima di definirne il contenuto***: in questo modo, quando nel codice si incontrerà tale identificatore, il compilatore sa che esso è stato definito e se abbiamo effettuato correttamente la chiamata, anche se non sa ancora dove trovarne il corpo.

Per scrivere una *forward declaration* è necessario usare una ***function declaration***, chiamata più spesso ***function prototype***: questa è composta da:
- Tipo di ritorno della funzione;
- Identificatore della funzione;
- Parametri della funzione, posti tra tonde e ciascuno avente davanti il tipo di tale parametro;
- Un punto e virgola per terminazione.
```cpp
<data_type> my_function(<param_type> my_parameter);
int add(int a, int b);
```
Come si nota ***non è presente il corpo della funzione***. Inserendo la *forward declaration* nel codice iniziale, il programma non restituirà un errore, poiché già conosce l'identificatore `add`:
```cpp
#include <iostream>

int add(int a, int b); // Forward declaration

int main() {
	std::cout << "La somma tra 2 e 3 fa: " << add(2,3) << '.\n';
	return 0;
}

int add(int a, int b) {
	return a + b;
}
```
È possibile anche non specificare i nomi dei parametri nel prototipo della funzione, ma non è una buona pratica.

Nel caso ci dimenticassimo il corpo della funzione di cui abbiamo fatto la *forward declaration*, verrà restituito ***un errore di linker***: in particolare il linker non riuscirà a collegare il prototipo a una corrispettiva funzione.

Le *forward declaration* non esistono solo per le funzioni, ma anche per ***variabili e tipi***: vedremo in seguito come possono essere realizzate.
### Perché l'Opzione 2 risulta migliore
È normale chiedersi perché utilizzare le *forward declaration* se il problema è risolvibile semplicemente riordinando il codice. I motivi sono vari:
- Spesso le *forward declaration* vengono utilizzate per comunicare al compilatore **l'esistenza di funzioni presenti anche in file esterni al codice**. Non è proprio possibile effettuare un riordinamento in questo caso, perché il chiamante e la funzione chiamata sono in ***due file separati***.
- È possibile utilizzare le *forward declaration* per rendere il codice più facile da leggere e interpretare: per esempio raggruppando i prototipi di funzioni che svolgono funzioni simili o su input simili, ecc...;
- Quando si hanno due funzioni che chiamano l'un l'altra non è possibile effettuare un riordine - la *forward declaration* giunge anche in questo caso in aiuto.

### Dichiarazione vs. Definizione
Adesso che abbiamo una base solida da cui partire è bene specificare ***la differenza tra definizione e dichiarazione***.

Si parla di ***dichiarazione*** quando viene comunicato al compilatore **l'esistenza di un certo identificatore** e i dati ad essi associati (tipo di dato e parametri nel caso di funzioni).

Si parla di ***definizione*** quando si ha una ***dichiarazione*** che però **implementano** (nel caso di funzioni o tipi) o **istanziano** (nel caso di variabili) **l'identificatore**.

In C++ **tutte le definizioni sono dichiarazioni**, ma non vale il viceversa. Le dichiarazioni che non sono definizioni si chiamano ***dichiarazioni pure***: un esempio di dichiarazione pura è la *forward declaration*.

Il compilatore si assume che, quando viene richiamato un identificatore, esso sia stato almeno ***dichiarato*** nel codice (non ha necessità che esso sia definito) - ci sono però delle eccezioni in cui il compilatore ha la necessità di una ***definizione***.
Nel nostro caso chiameremo **dichiarazione** tutto ciò che è una **dichiarazione pura**, mentre chiameremo **definizione** tutto ciò che è sia una **definizione che una dichiarazione**.

### One Definition Rule (ODR)
La ***One Definition Rule*** abbreviata in ***ODR*** è una regola fondamentale delle dichiarazioni del C++. Essa si basa su 3 parti:
1) ***All'interno di un file***, ogni funzione, variabile, tipo o *template* **in un certo *[[2.5 ~ Introduction to local scope#Scope & Local scope|scope]]* deve possedere esattamente una definizione***. Definizioni che avvengono in *scope* diversi non violano questa regola;
2) ***All'interno di un programma***, ogni funzione e variabile **in un certo *scope* deve possedere esattamente una definizione**. Questa regola esiste siccome i programmi possono essere formati da più file. Funzioni e variabili non visibili dal *linker* sono esclusi da questa regola;
3) Tipi, *templates*, funzioni *inline* e variabili *inline* possono avere **definizioni duplicate in file differenti** a patto che la loro definizione sia **identica**.

Violare la regola 1 dell'ODR genererà un **errore di compilazione** di ***redefinizione***.-
Violare la regola 2 dell'ODR genererà un **errore di linker** di ***redefinizione***.
Violare la regola 3 dell'ODR genererà ***[[1.6 ~ Uninitialized variables and undefined behavior#Undefined behavior|undefined behavior]]***.
