Nella [[7.3 ~ Local Variables|lezione dedicata alle variabili locali]] abbiamo introdotto il concetto di ***linkage***, ossia una proprietà di un identificatore che determina **se successive dichiarazioni di tale identificatore *fanno o meno riferimento allo stesso oggetto***. Abbiamo anche visto che *le variabili locali ***non hanno linkage***, ossia che ogni definizione successiva di una variabile locale fa riferimento ad oggetti ogni volta diversi.

Le **variabili locali** e **gli identificatori di funzione** possono avere ***internal linkage*** o ***external linkage***, a seconda dei casi. In questa lezione ci occuperemo dei casi in cui hanno *internal linkage*, mentre nella successiva di quelli in cui hanno *external linkage*.

Un identificatore con ***internal linkage*** può essere ***visto e usato da una sola translation unit***, ma *non è accessibile da altre translation unit*. Questo significa che **se due file sorgenti hanno due identificatori avente stesso nome**, ***questi verranno trattati come indipendenti***.

#### Variabili globali con *internal linkage*
Le [[7.4 ~ Introduction to global variables|variabili globali]] che hanno *internal linkage* vengono chiamate ***internal variables***.

È possibile assegnare *internal linkage* ad una **variabile globale *non costante*** tramite la ***keyword* `static`**; variabili globali [[5.1 ~ Constant variables (named constants)|costanti]] o [[5.6 ~ Constexpr variables|constexpr]] ***hanno internal linkage di default***, per cui inserire la keyword `static` risulta ridondante.

Vediamo un esempio con file multipli che usano *internal variables*:
`a.cpp`:
```cpp
// Internal variable, siccome constexpr globale.
[[maybe_unused]] constexpr int g_x { 2 };
```
`main.cpp`:
```cpp
#include <iostream>

// Internal variable, siccome constexpr globale
constexpr int g_x { 3 }; 

int main() {
	std::cout << g_x << '\n';
	return 0;
}
```
Questo programma stampa `3`, in quanto viene utilizzata la ***internal variable*** `g_x` di `main.cpp`, mentre quella di `a.cpp` viene semplicemente ignorata.

Il fatto che le variabili costanti o constexpr abbiano *di default* ***internal linkage*** è dovuto dal fatto che ***è possibile inserirle all'interno di header files*** e quindi propagabili ad ogni file che include tale header.

#### Funzioni con *internal linkage*
Anche gli identificatori di funzioni hanno la proprietà di *linkage*. Le funzioni sono, di default, a ***external linkage***, ma può essere forzato ***internal linkage*** tramite la *keyword* `static`.
Vediamo un esempio:
`a.cpp`
```cpp
// Questa funzione viene vista solo qui dentro
// In quanto abbiamo inserito la keyword static.

[[maybe_unused]] static int add(int x, int y) {
	return x + y;
}
```
`main.cpp`
```cpp
#include <iostream>

// Forward declaration per la funzione add()
int add(int x, int y);

int main() {
	std::cout << add(1, 2) << '\n';
	
	return 0;
}
```
Questo programma, alla compilazione, darà ***errore di linker***:
- `add()` è stata definita all'interno di `a.cpp`, ma essendo `static` essa è visibile **solamente all'interno di `a.cpp`**.
- La ***forward declaration*** di `add()` in `main.cpp` **non viene propagata**, in quanto non riesce a vedere una definizione in nessun file, quindi verrà generato errore di linker.

#### La *One Definition Rule* e l'*internal linkage*
Nella lezione legata alla [[2.7 ~ Forward declarations and definitions#One Definition Rule (ODR)|forward declaration]] abbiamo parlato della ***One Definition Rule***, ossia del fatto che ***un identificatore non può avere più di una definizione nello stesso codice***.

Tuttavia è bene notare che ***internal variables e funzioni*** definite in diversi file **sono considerate entità indipendenti**, pertanto **la One Definition Rule non viene violata *tra file*** (nonostante ciò può essere violata all'interno di uno stesso file).

#### `static` vs unnamed namespaces
Ad oggi, la keyword `static` sta cadendo in disuso in favore degli ***unnamed namespaces***, che oltre a fornire *internal linkage* ad una vasta gamma di identificatori sono meglio realizzati per **garantire internal linkage ad un insieme di identificatori**.

Vedremo gli *unnamed namespaces* in seguito.

#### Perchè dare *internal linkage* agli identificatori?
Ci sono due motivi principali per cui si ha preferenza **la forzatura di *internal linkage* su identificatori**:
- Rendere un certo identificatore ***accessibile solo all'interno di un solo file e non di altri***, per esempio una variabile globale utile alle funzioni solo di un certo file ma non di altri.
- Per essere più sicuri **nell'evitare *naming collisions***, spesso tramite più file. Se una *naming collision* coinvolge una variabile che ha *internal linkage*, allora essa è avvenuta **all'interno del file**, riducendo le cose da controllare per risolverlo.
Molte guide consigliano **di forzare *internal linkage* a variabili che vengono usate solo all'interno di un file singolo**.
