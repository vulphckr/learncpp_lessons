In una delle [[1.10 ~ Introduction to expressions|prime lezioni]] abbiamo introdotto il concetto di ***expression***. Di default, una qualsiasi espressione viene **valutata in *runtime***, e in alcuni casi **diventa necessario**, come ad esempio le espressioni che contengono input e output, le quali devono essere svolte necessariamente in runtime, poichè non è possibile svolgerle in compile-time.

Nella [[5.4 ~ The as-if rule and compile-time optimization|scorsa lezione]] abbiamo parlato della ***as-if rule*** e di come il compilatore può effettuare ottimizzazioni valutando alcune espressioni a *compile-time* anzichè in *runtime*.
```cpp
const double x { 1.2 };
const double y { 3.4 };
const dobule z { x + y }; // x + y può essere valutata a runtime o compile-time
```
Di norma, l'espressione `x + y` viene valutata a *runtime*, tuttavia, siccome `x` e `y` **sono costanti** e dunque **conosciute a compile-time** quando `x + y` viene valutata, se il compilatore effettua ottimizzazioni (*constant folding* e *constant propagation*) tale espressione potrebbe essere valutata a *compile-time*.

Ci sono altri casi in cui C++ **deve necessariamente valutare il valore di un espressione**, come nel caso della variabili `constexpr`; nei casi in cui è necessaria, ma non viene fornita, il compilatore restituirà un errore.

##### Benefici della programmazione *compile-time*
Siccome la *as-if rule* viene applicata in modo silenzioso, non sappiamo quali parti di codice vengono eseguiti in *runtime* e quali vengono eseguiti in *compile-time* - questo significa che, utilizzando diversi compilatori o su diverse macchine, il codice risultante potrebbe essere diverso.

Per migliorare questa situazione, C++ mette a disposizione degli strumenti che rendono al compilatore **esplicito il fatto di compilare il codice a *compile-time***. L'esecuzione di istruzioni che fanno uso di questi strumenti prende il nome di ***compile-time programming***.

Nota bene che ***la compile-time programming non dipende dalle ottimizzazioni, e se richiesta verrà sempre eseguita a compile-time***.

Questi strumenti aiutano molto la compilazione del codice sotto gli aspetti di:
- Performance, rendendo il codice più leggero e veloce;
- Versatilità, rendendo tali istruzioni sempre eseguibili in qualsiasi contesto;
- Prevedibilità, generando errori nel momento in cui il codice non può essere eseguito a *compile-time*;
- Qualità, generando errori direttamente in compilazione, molto più facili da risolvere rispetto a errori in runtime - oltre al fatto che a *compile-time* il concetto di [[1.6 ~ Uninitialized variables and undefined behavior#Undefined behavior|undefined behavior]] non esiste.

Gli strumenti che vedremo nelle prossime lezioni che permettono forzatamente l'esecuzione di codice a *compile-time* sono:
- Variabili `constexpr`;
- Funzioni `constexpr`;
- Templates;
- `static_assert`.
Tutte queste funzioni hanno in comune una cosa: fanno uso di ***constant expressions***.
#### Constant Expressions
La definizione di ***constant expression*** non viene espressamente fornita dal linguaggio: lo standard definisce ciò che è una *constant expression* assieme alle regole che determinano come il compilatore deve operare con queste ultime.

Quando abbiamo introdotto le espressioni, esse sono state definite come "le sequenze non vuote di *literal*, variabili, operatori e chiamate a funzioni che calcolano un valore finale". Una ***constant expression*** (*espressione costante*) è una espressione formata da *literals*, variabili **costanti**, operatori e chiamate a funzione, in cui **ogni parte di cui è composta tale espressione deve essere eseguibile a *compile-time***.

Un espressione che non è una *constant expression* è detta una ***runtime expression***, in quanto deve essere necessariamente valutata a *runtime*.

#### Cosa può contenere una *constant expression*?
Una *constant expression* può essere formata dalle seguenti componenti:
- Altre *constant expressions* (ossia sono **componibili**);
- [[5.2 ~ Literals|Literals]], in quanto valori costanti - es: `5`, `1.2`, `"Hello world!";
- La maggior parte degli **operatori**, su cui agiscono **operandi costanti** - es: `3 + 4`, `2 * sizeof(int)`.
- Integrali costanti (di tipo`const`, vedi [[5.1 ~ Constant variables (named constants)|questa lezione sui const]]), con un valore di inizializzazione costante (quindi anche un'altra *constant expression*) - es: `const int x { 5 }`; questa è una eccezione, in quanto si preferisce usare le variabili `constexpr`.  
- Variabili `constexpr`, che vedremo in seguito;
- Chiamate a funzioni `constexpr`, con argomenti costanti, che vedremo in seguito.
Introduciamo anche le seguenti nomenclature:
- "$X$ può essere usato in una *constant expression*" è spesso usato per indicare che cos'è $X$, ossia un qualcosa che ***può far parte*** di una *constant expression*;
- "$X$ è una *constant expression*" viene spesso usato per indicare che una specifica espressione $X$ è anche una *constant expression*.

#### Quando avviene la valutazione di una *constant expression*
Seppure abbiamo detto che una *constant expression* può essere sempre valutata a *compile-time*, **non è detto che venga sempre valutata a *compile-time***.
Il compilatore **valuterà le *constant expression* solo nei contesti in cui esse sono necessarie**, in caso contrario, esso decide se tale espressione deve essere valutata in *runtime* o *compile-time*.
```cpp
const int x { 3 + 5 };
int y { 4 + 5 };
```
- La variabile `x` è di tipo `const int` e ha un valore di inizializzazione costante (*una constant expression*), quindi `x` può essere usata in altre *constant expressions*. L'espressione `3 + 5` **deve quindi essere valutata a compile-time**, siccome se non lo fosse, `x` non sarebbe una *constant expression* perchè non sarebbe valutabile a compile-time.
- La variabile `y` è di tipo `int`; non essendo costante, essa non è usabile in una *constant expression* - il valore di inizializzazione, `4 + 5` è tuttavia una *constant expression*, ma siccome non si ha la necessità di valutarla non è detto che essa sia valutata a compile-time.

*Solitamente*, se le ottimizzazioni sono abilitate, il compilatore valuterà le *constant expression* anche quando non richieste. 

#### Perchè le espressioni compile-time devono essere costanti?
```cpp
#include <iostream>

int main() {
    int x { 5 };
	// Da qui, x è conosciuto al compilatore
    std::cin >> x; // Lettura di x da parte dell'utente
	// Da qui il valore di x è sconosciuto al compilatore
    return 0;
}
```
In questo codice, inizialmente la variabile `x` viene inizializzata a `5`, ed è qui conosciuta al compilatore. Tuttavia, in seguito, l'utente inserirà un nuovo valore per `x` tramite `std::cin` - da questo punto in poi, il compilatore non conoscerà più il valore per `x`. In questo caso, il valore di `x` **non è sempre valutabile a compile-time** violando il fatto che una tale espressione debba essere sempre valutabile a compile-time. 

Siccome le costanti non possono cambiare il loro valore, una volta inizializzate con un valore costante, il compilatore ne conoscerà sempre il valore ed esso non cambierà mai. Questo rende le cose più semplici: se il compilatore sarebbe stato molto più complesso da realizzare se dovesse tenere traccia del valore di ogni variabile in ogni dato momento della compilazione.
