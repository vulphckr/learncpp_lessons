Nella [[5.5 ~ Constant Expressions|scorsa lezione]] abbiamo definito le ***constant expressions***, perchè il loro uso è desiderabile (i vantaggi del *compile-time programming*) e abbiamo concluso spiegando quando una espressione viene *sicuramente* valutata in *compile-time*.

In questa lezione vedremo come creare delle **variabili** che possono essere **usate in *constant expressions***, e vedremo il primo metodo per **assicurare una valutazione compile-time di espressioni**.

#### Il problema con `const` e la compile-time evaluation assicurata
Abbiamo visto, nella scorsa lezione, che tramite una [[5.1 ~ Constant variables (named constants)|variabile costante]] (di tipo `const`) è possibile creare una variabile la quale può essere usata all'interno di una *constant expression*.

**Una variabile `const` con un valore di inizializzazione costante può essere usata all'interno di *constant expressions***; in qualsiasi altro caso, una variabile `const` non può essere usata all'interno di *constant expressions*.

Tuttavia, ci sono alcuni problemi che riguarda l'uso di variabili `const` per creare valori usabili in una *constant expression*.

Prima di tutto, `const` non ci **garantisce** se la variabile è usabile o meno in una *constant expression*, ma dipende da come essa è inizializzata; ad esempio, nel seguente codice, è abbastanza semplice:
```cpp
int a { 5 }; // Chiaramente non costante
const int b { a }; // b non può essere usata in una constant expression - a non è un valore di inizializzazione costante.
const int c { 5 }; // c può essere usata in una constant expression - c è un valore di inizializzazione costante.
```
Ma può diventare complesso in codici molto complessi:
```cpp
const int d { someVar }; // someVar è costante?
const int e { getValue() }; // getValue() è costante?
```
`d` ed `e` ***potrebbero*** essere usate in *constant expressions*, dipende però da come sono definite `someVar` e `getValue()` - queste ultime potrebbero a loro volta essere definite da altre variabili, e così a cascata - **non è per niente chiaro** se i valori usati sono costanti o meno.

Dopodichè, l'uso di `const` **non comunica al compilatore** che la variabile a cui è associata può essere usata in una *constant expression*. 

Infine, l'uso di `const` per crerare variabili costanti a *compile-time* è limitato agli **integrals** - **non è possibile utilizzare la *keyword* per variabili costanti *non-integral***.

#### La *keyword* `constexpr`
Fortunatamente possiamo **chiedere al compilatore di garantire di ottenere una variabile costante a *compile-time*** ogni volta che ci è necessario. Questo è possibile tramite la *keyword* `constexpr`, usata al posto di `const` in una dichiarazione di variabile costante. 

**Una variabile `constexpr` è sempre una costante compile-time**. 
Il risultato di ciò è che **una variabile `constexpr` deve necessariamente essere inizializzata con una *constant expression***, altrimenti il compilatore restituirà un errore.
(Abbiamo visto cosa è una *constant expression* [[5.5 ~ Constant Expressions#Cosa può contenere una *constant expression*?|qui]]).

Inoltre, le `constexpr` possono contenere anche valori **non integral!** (possono essere ad esempio `float`, `double`...).

#### `const` vs `constexpr`
Tiriamo le somme e vediamo le differenze tra `const` e `constexpr`.
In una variabile:
- `const`significa che **il valore della variabile non può cambiare dopo che essa è stata inizializzata**. Il valore di inizializzazione può essere noto a compile-time o runtime, ma il valore può essere valutato in runtime.
- `constexpr` significa che **la variabile può essere usata in una *constant expression***. Il valore di inizializzazione ***deve*** essere noto a compile-time, ma il valore può essere valutato in *compile-time* o in runtime.

Le variabili `constexpr` sono *implicitamente `const`*, ma al contrario le `const` non sono implicitamente `constexpr`. Entrambe le *keyword* possono essere usate contemporaneamente, ma è ridondante. 

Al contrario di `const`, `constexpr` **non diventa parte del tipo della variabile a cui viene associata**. Una variabile dichiarata come `constexpr int`, ha tipo `const int` per l'implicazione che ha `constexpr` nei confronti di `const`. 

La ***best practice*** è quindi:
- Qualsiasi variabile costante che **è inizializzata a una *constant expression*** deve essere dichiarata `constexpr`;
- Qualsiasi variabile costante che **non è inizializzata a una *constant expression*** deve essere dichiarata `const`;
- Per oggetti **non compatibili con `constexpr`** (vedremo poi quali sono) si utilizza `const`.

Da ora in avanti, chiameremo per semplicità le *constant expressions* come `constexpr`, in quanto i due termini sono praticamente equivalenti.

#### Parametri di funzione `const` e `constexpr`
Le chiamate a funzione vengono valutate **a runtime**, con gli *argomenti* forniti che vengono usati per inizializzare i suoi parametri. Siccome l'inizializzazione dei parametri ***avviene a runtime*** questo ha due conseguenze fondamentali per i tipi costanti visti finora:
- I parametri di tipo `const` **sono trattati come costanti runtime**. 
- I parametri di funzione ***non possono essere dichiarati `constexpr`***, siccome la loro inizializzazione avviene solo in runtime.

##### Recap Nomenclatura delle ultime due lezioni
- ***Compile-time constant***: Un valore o un oggetto **non modificabile** il cui valore **deve essere noto a compile time**. (Es. *literals* o variabili `constexpr`)
- ***Constexpr***: **Una *keyword*** che serve a **dichiarare oggetti come *compile-time constants***. Informalmente, l'abbreviazione di *constant expression*.
- ***Constant expression***: **Un'espressione** che contiene solamente ***compile-time constants*** e **operatori che supportano valutazione compile-time**.
- ***Runtime expression***: **Un'espressione** che **non è una *constant expression***.
- ***Runtime constant***: Un valore o un oggetto **non modificabile** che **non è una ***compile-time constant***. 

#### Breve introduzione alle funzioni `constexpr`
Una **funzione constexpr** è una funzione **che può essere chiamata all'interno di una *constant expression***. 
Una funzione constexpr deve essere **necessariamente valutata a compile-time** quando ***essa fa parte di una espressione che deve essere valutata a compile-time***. Se questo non succede, allora la funzione viene valutata a *compile-time*, se idonea, oppure a *runtime* se non lo è. È idonea per esecuzione *compile-time* se **tutti gli argomenti passati alla funzione sono *constant expressions***.
