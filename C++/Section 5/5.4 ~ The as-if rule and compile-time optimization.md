#### Ottimizzazione
In programmazione, si chiama ***ottimizzazione*** il processo di modificare del software al fine di renderlo più efficiente (ossia facendogli usare meno risorse o farlo andare più veloce).

Alcune ottimizzazioni vengono fatte a mano - viene spesso fatto uso di un programma chiamato **profiler** per visualizzare i tempi di esecuzione di ogni zona di un dato codice, e quali invece stanno impattando sulle performance. Dopo aver evidenziato quali zone di codice sono problematiche, è il programmatore a modificarle, cercando di renderle più efficienti. 
Solitamente si preferiscono miglioramenti ad alto livello, che migliorano di molto le performance (per esempio usare un algoritmo più veloce, ottimizzare l'accesso ai dati, rendere un certo compito parallelizzabile...).

Altre ottimizzazione vengono fatte **automaticamente** da un programma che ha il compito di **ottimizzare altri programmi**, detto ***optimizer***. Gli optimizer spesso lavorano a *basso livello*, cercando di effettuare delle ottimizzazioni su espressioni che possono essere scritte in modo da renderle più efficienti. 
Per esempio, l'espressione `i = i * 2` può essere riscritta come `i *= 2`, `i += i` oppure `i <<= 1` - per un dato di tipo *integral* tutte queste espressioni sono uguali alla iniziale, ma su un dato sistema una potrebbe risultare più efficiente delle altre; un programmatore potrebbe non sapere quale delle tre è la più efficiente, mentre un optimizer si.
I miglioramenti fatti da un optimizer a basso livelli spesso non sono così impattanti, tuttavia la loro totalità è significativa per le performance di un programma.

I compilatori più moderni, oltre alla compilazione, fanno anche da optimizer. In modo simile al [[2.10 ~ Introduction to the preprocessor|preprocessore]], queste ottimizzazioni non modificano il codice - ma vengono applicate in modo trasparente al codice compilato. 

Effettuare un'ottimizzazione ha spesso un *tradeoff* tra spazio e tempo d'esecuzione. È possibile indicare al compilatore se preferire una ottimizzazione che favorisce l'una o l'altra e anche il grado di tale ottimizzazione. Di default, la maggior parte dei compilatori **non effettua ottimizzazioni**, pertanto se sono richieste, vanno abilitate.

#### The as-if rule
Le ottimizzazioni effettuabili su un programma possono essere di vario tipo - ma un'ottimizzazione può essere effettuata seguendo la ***as-if rule***. 

Questa regola dice che **un programma può essere modificato in qualunque modo** al fine di produrre ottimizzazioni, **a patto che il comportamento osservabile del programma risultante sia lo stesso di quello iniziale**.
	*Esistono eccezioni a questa regola, che vedremo molto più avanti*.

Esistono diverse ottimizzazioni attuabili che portano alla produzione di codice che è perfettamente identico a quello iniziale mantenendone il comportamento.

#### Una possibilità di ottimizzazione
Consideriamo il seguente codice:
```cpp
#include <iostream>

int main() {
	int x { 3 + 4 };
	std::cout << x << '\n';
	
	return 0;
}
```
Senza applicare ottimizzazioni, il compilatore produrrà un programma che calcolerà l'espressione `3 + 4` ogni volta che il programma viene eseguito.

Se il programma venisse eseguito un milione di volte, la CPU eseguirà per un milione di volte il calcolo `3 + 4`, producendo `7` un milione di volte.

Siccome il risultato di `3 + 4` non cambia mai, calcolarlo così tante volte è uno spreco di risorse. Questo programma è ottimizzabile?

#### Compile-time evaluation
I compilatori di C++ moderni sono in grado di **valutare certe espressioni in *compile-time***. (la fase di compilazione viene detta ***compile-time***, in contrapposizione alla fase di esecuzione detta ***runtime***). Quando il compilatore valuta in parte o totalmente una espressione in fase di compilazione di un programma, questa valutazione prende il nome di ***compile-time evaluation***.

In questa lezione vedremo alcune strategia di *compile-time evaluation*, in modo da capire a grandi linee come viene effettuata un'ottimizzazione.

##### Constant folding
Il ***constant folding*** è una delle più comuni strategie di *compile-time evaluation*. Questa consiste nel **sostituire espressioni composte da *literal* con il risultato di tale espressione***.

Nell'esempio di prima e sfruttando *costant folding* l'espressione `3 + 4` viene sostituita dal suo risultato, `7`. Ora il programma non dovrà calcolare ad ogni esecuzione `3 + 4`. 

Il *costant folding* può essere applicato anche a sottoespressioni:
```cpp
#include <iostream>

int main() {
	std::cout << 3 + 4 << '\n';

	return 0;
}
```
Anche in questo caso, `3 + 4` viene calcolato dal compilatore, diventando il valore `7` ed evitando il calcolo ad ogni esecuzione.

##### Constant propagation
Il *constant folding* ha dato vita al seguente codice:
```cpp
#include <iostream>

int main() {
	int x { 7 };
	std::cout << x << '\n';
	
	return 0;
}
```
Il quale è ancora ottimizzabile: quando inizializziamo `x`, il valore `7` viene allocato nella porzione di memoria riservata ad `x`. Quando effettuiamo la stampa di `x`, il valore `7` deve essere ripescato dalla zona di memoria riservata ad `x`. In due linee di codice abbiamo fatto due accessi in memoria, uno di memorizzazione del valore, l'altro di ripescaggio.

La ***constant propagation*** è una tecnica di ottimizzazione in cui **il compilatore rimpiazza le variabili aventi valore costante con tale valore**. Siccome `x` ha valore `7`, costante per tutta l'esecuzione del programma, per mezzo della *constant propagation*, il valore `7` verrà rimpiazzato ogni volta che verrà usata `x`. Questa operazione risparmia accessi in memoria.

```cpp
#include <iostream>

int main() {
	int x { 7 };
	int y { 3 };
	std::cout << x + y << '\n';

	return 0;
}
```
In questo esempio:
- La ***constant propagation*** trasforma l'espressione `x + y` in `7 + 3`;
- Il ***constant folding*** trasforma l'espressione `7 + 3` in `10`.
Risparmiando di fatto 2 accessi in memoria e un calcolo ad ogni esecuzione!

##### Dead code elimination
Il ***dead code elimination*** è una pratica di ottimizzazione dove **il compilatore rimuove codice che potrebbe essere eseguito, ma non ha effetto sul comportamento del programma***.

Supponiamo di avere il codice ottimizzato da prima:
```cpp
#include <iostream>

int main() {
	int x { 7 };
	std::cout << 7 << '\n';

	return 0;
}
```
La variabile `x` viene inizializzata, ma mai utilizzata. L'istruzione di dichiarazione e inizializzazione è inutile e pertanto può essere rimossa. Il risultato ottimizzato per ***dead code elimination*** è il seguente:
```cpp
#include <iostream>

int main() {
	std::cout << 7 << '\n';

	return 0;
}
```
Che è un codice che ha comportamento equivalente a quello iniziale. 

##### Const variables are easier to optimize
In alcuni casi, ci sono cose molto semplici che rendono la vita del compilatore molto più semplice. 

La *constant propagation* può essere difficile da eseguire per un optimizer - in particolare identificare quali variabili sono effettivamente costanti e quali sono soggette a cambiamenti e poi applicare l'ottimizzazione nel caso sia necessario. 

Possiamo aiutare il compilatore nell'ottimizzazione **utilizzando, quando possibile e necessario variabili `const`**.

```cpp
#include <iostream>

int main() {
	const int x { 7 }; // x è const
	std::cout << x << '\n';

	return 0;
}
```
Siccome `x` è ora `const`, il compilatore avrà la garanzia che, una volta inizializzata, la variabile non cambierà il suo valore, effettuando tutte le ottimizzazioni necessarie.

#### Ottimizzazione e debugging
Se l'ottimizzazione rende i programmi più efficienti, perchè essa non è abilitata di default?

Quando un programma viene ottimizzato, il risultato è il programma iniziale con variabili o espressioni diverse, che però hanno lo stesso comportamento del programma iniziale. Questo rende **il debugging particolarmente difficile da eseguire**, siccome il programma in esecuzione non corrisponde esattamente al codice scritto. 

Al fine di minimizzare i dubbi sul debugging, di *default* le ottimizzazioni sono disabilitate. 

#### Compile-Time constants vs Runtime constants

Tutto ciò che avviene nella fase che inizia dalla compilazione del codice alla produzione del corrispondente eseguibile avviene in ***compile-time***. In *compile-time* avvengono, per esempio, le **ottimizzazioni** e **gli errori di compilazione**.

Tutto ciò che invece avviene durante l'esecuzione del programma fino alla sua terminazione (prematura o meno), avviene in ***runtime***. In *runtime* può avvenire, per esempio, ***undefined behavior***.

Le costanti in C++ sono separate in due categorie informali:
- ***Compile-Time constants***: è una costante **il cui valore è noto in compile-time**. Esempi di questi sono:
	- *Literals*;
	- Oggetti costanti inizializzati a valori costanti in *compile-time*.
- ***Runtime constants***: è una costante **il cui valore viene determinato in runtime**. Esempi di questi sono:
	- Parametri di funzione costanti;
	- Oggetti costanti inizializzati a valori costanti in *runtime*.
```cpp
#include <iostream>

int five()
{
    return 5;
}

int pass(const int x) // x è una costante runtime
{
    return x;
}

int main()
{
    // Questa non è una costante:
    [[maybe_unused]] int a { 5 };

    // Queste sono costanti compile-time:
    [[maybe_unused]] const int b { 5 };
    [[maybe_unused]] const double c { 1.2 };
    // Essendo b una costante compile-time, anche d è una costante compile-time
    [[maybe_unused]] const int d { b };

    // Queste sono costanti runtime:
    [[maybe_unused]] const int e { a }; // a non è costante
    // e è una costante runtime, quindi lo diventa anche f
    [[maybe_unused]] const int f { e };
    // il valore di ritorno di five() è sconosciuto finchè non viene eseguita
    [[maybe_unused]] const int g { five() }; 
    [[maybe_unused]] const int h { pass(5) }; // stesso discorso

    return 0;
}
```
Le definizioni date **non sono rigorose**, anche se vengono spesso utilizzate:
- Alcune *costanti runtime* vengono comunque calcolate in compile-time per ottimizzazione;
- Alcune *costanti compile-time* non possono essere usate in alcune funzionalità compile-time.
Approfondiremo le due classi di costante nelle prossime lezioni.
